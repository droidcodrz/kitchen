### 3.2 Deletion guard for in-use records — client request

**Problem.** Products and inventory items could be deleted while open projects depended on them, leaving those projects' reserved and consumed stock referring to records that no longer existed. Clients were already protected this way; these two were not.

**Implementation.**
- Refused in both controllers, with a message naming how many projects are affected.
- The delete control is disabled up front with the reason on hover, rather than opening a dialog only to refuse — following the client's explicit feedback on that pattern.
- For materials, both dependency routes count: attached **directly** to a project, and required through a **product's bill of materials**. Counted over projects, so a project using a material both ways counts once.
- The set of statuses treated as "closed" is a shared constant, so the product and material rules cannot drift apart.
- List pages carry the counts from the index query rather than querying per row, avoiding N+1 on two frequently-used screens.

### 3.3 Production deploy unblocked — migrations

**Problem.** `php artisan migrate` aborted on a duplicate column. Because Laravel halts the entire run at the first failure, **every subsequent migration stayed unapplied** — including the table required by the new Inventory Items feature. This was a blocked deploy, not a single broken migration.

**Investigation.** Rather than patch the one that failed, all migrations were audited. Two distinct classes of problem were found:

1. **Assumed-absent schema** — 10 column migrations, 32 create-table migrations and 2 index/constraint migrations assumed their schema did not already exist. Any of them would abort a deploy the same way.
2. **MySQL-only syntax** — two migrations used raw `ALTER TABLE … MODIFY`, which no other driver understands, so a fresh install on SQLite could never complete.

**Implementation.** Every migration now checks before acting. Multi-column migrations check per column, so a partially-applied table completes rather than being skipped wholesale; the three framework migrations that create several tables each check per table. The two raw-SQL migrations use the schema builder, with the MySQL-only form retained in `down()` only when running on MySQL.

**Verification.**

| Test | Result |
|---|---|
| Build from an empty database, seeded | 46 migrations, **0 failures** |
| Delete every migration record, keep all tables and data, replay all 46 | **0 failures** |
| Data after replay | users 11, projects 6, products 11, inventory 10 — **unchanged** |
| Application after rebuild | 11 pages load, no JavaScript errors |

*Caveat:* verified on SQLite; production is MySQL. The guards used are driver-agnostic, but this was not exercised against MySQL directly.

### 3.6 Every form silently failing after in-app navigation

The most significant defect of the two days.

**Reported:** a project deleted once, restored from the Waste Bin, then could not be deleted again — no request, no error, nothing.

**Investigation.** Two false starts, both recorded in §4:
1. First attributed to the submit button being disabled mid-submit. A/B testing against the old code disproved it.
2. Delete then appeared to work — because it was tested with a fresh page load, which is exactly the condition under which the fault does not occur.

Instrumenting the network revealed the decisive evidence: clicking Delete produced **no request at all**, with the form action correct and the button enabled.

**Root cause.** `wire:navigate` swaps the page body and re-runs the scripts inside it, but the double-submit guard registers its listener on `document`, which survives the swap. Each navigation added another copy. On the next submit, the first copy flagged the form as in-flight and the second copy — seeing that flag already set — cancelled the submit as a duplicate.

A single in-app navigation was enough to break **every form in the application**. A full page reload restored normal behaviour, which is why the failure looked intermittent and why restoring from the Waste Bin appeared to trigger it: reaching the Waste Bin and returning *is* navigation.

**Fix.** The guard installs once per document. Two further jamming paths were closed at the same time, both confirmed by A/B test:
- A submit cancelled by another handler — the New Project form does this on a duplicate name — left the form flagged permanently, silently swallowing every later click.
- A submit that never navigates now releases the form after a timeout instead of jamming for the rest of the visit.

**Verification.**

| Check | Result |
|---|---|
| Delete after in-app navigation | POST 302 |
| Delete a restored project — the reported case | POST 302 |
| Delete after several navigations | POST 302 |
| Guard installed exactly once | confirmed |
| Create form after navigation | works |
| Three rapid clicks on Delete | **one request** — original protection intact |

## 4. Corrections and lessons

Recorded deliberately. Two of the three defects on 19 August were regressions from my own changes, and one verification claim was wrong.

### 4.1 A QA item was reported fixed when it was not
QA #2 (remove-line control on equipment rows) was verified against `/projects/create`, while the reported problem was in the New Project modal — a different form with different markup. The claim was wrong. Both forms now have the control.

### 4.2 A wrong diagnosis, reported rather than shipped
The delete failure was first attributed to the submit button being disabled during submission. Testing that hypothesis against the old code showed identical behaviour, disproving it. This was reported as incorrect rather than shipping a fix built on a false premise.

### 4.3 A test method that concealed the defect
Delete was verified using a direct page load. The fault only appears after in-app navigation, so the test could never have caught it. Subsequent tests navigate the way a user does.

### 4.4 Guard changes carry wide blast radius
The double-submit guard introduced on 18 August caused both §3.4 and §3.6. Anything installed globally across every form warrants testing after navigation, not only on first load.

**Standing takeaway:** several screens have both a modal on the list page and a separate full form. Fixing or verifying one does not cover the other. Both are now treated as a pair.
