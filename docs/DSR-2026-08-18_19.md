## Day 2 — Wednesday, 19 August 2026

### Objective
Client-requested deletion rule, plus resolution of issues raised after the QA pass.

### 1. Deletion guard for in-use records — *client request*
Products and inventory items that open projects depend on could be deleted, leaving those projects' reserved and consumed stock pointing at records that no longer existed. Clients were already protected this way; these were not.

- Blocked server-side in both controllers, with a message naming the number of projects.
- The delete control is now disabled up front with the reason on hover, rather than opening a dialog to refuse.
- For materials, both routes count: attached **directly** to a project, and pulled in through a **product's bill of materials**. Counted over projects, so using a material both ways counts once.
- Verified: blocked correctly; a direct POST bypassing the UI was also refused; delivered and trashed projects correctly do **not** block; unused items still delete normally.

### 2. Deploy unblocked — migrations
`php artisan migrate` aborted on a duplicate column, leaving every later migration unapplied — including the table the new Inventory Items feature needs. This was a blocked deploy, not one broken migration.

- Audited all migrations: **10 column migrations, 32 create-table migrations and 2 index/constraint migrations** carried the same assumption.
- Two further migrations used MySQL-only raw SQL and could never run on any other driver.
- Verified from an empty database (**46 migrations, 0 failures**) and by wiping every migration record and replaying all 46 against a fully populated schema — **0 failures, row counts unchanged**.

## Corrections and lessons

Recorded deliberately, since two of today's defects were caused by my own earlier changes:

1. **QA #2 was reported fixed but was not.** I verified the remove-line control on `/projects/create` while the reported problem was in the New Project modal — a different form. Both are fixed now.
2. **A wrong first diagnosis on the delete failure.** I attributed it to the submit button being disabled mid-submit; A/B testing against the old code disproved it. Reported as wrong rather than shipped.
3. **A test method that hid the bug.** I verified delete using a fresh page load — precisely the case where the fault does not appear. Corrected to navigate the way a user does.

**Takeaway:** several screens have both a modal on the list page and a full form. Fixing or verifying one does not cover the other. Both are now checked as a pair.

```bash

```

`migrate` is required for the `project_inventory_item` table and the materials fix. `view:clear` matters because Blade caches compiled templates — without it the old markup persists and fixes appear not to work.
