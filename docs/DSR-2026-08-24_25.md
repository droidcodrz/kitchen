## 2. Day 1 — Monday, 24 August 2026

| # | Commit | Title | Files | +/− |

### 2.2 What was actually wrong

The theme lived in `localStorage` and nowhere else. Everything the application knew about a user's choice therefore existed in one browser on one machine. Signing in from a different computer, a different browser, a fresh profile or a private window came up light again, with no way to carry the preference across.

There was already somewhere to put it, unused:

- The `users` table carries a **`theme_preference`** column.
- There is a route, `PATCH /settings/theme`, to update it.

**Neither was connected to anything.** Measured in a browser: clicking the theme buttons produced **zero** requests to that route, and the column sat at its default `light` for every account while the real setting lived somewhere the server could not see.

| Check | Before | After |
|---|---|---|
| Requests reaching the server on a theme change | **0** | 1 per change |
| `theme_preference` in the database | stuck at `light` | follows the choice |
| Same user, different browser | **reset to light** | opens in the saved theme |

### 2.3 What changed

The topbar toggles and the Settings buttons now record the choice against the account. The switch still happens locally first and the request is deliberately fire-and-forget — a failure to record it must not undo or block a theme the user can already see. On the way back in, the saved preference seeds the browser before first paint, so it applies without a flash.

Two smaller faults were fixed alongside:

- The update rule accepted `system`, which the column — an enum of `light` and `dark` — cannot store. A request for it passed validation and then failed at the database. Nothing in the interface offers that option, so the rule now matches what can actually be saved.
- The Settings buttons took their highlight from `localStorage`, so a browser that had never set it showed the wrong button as selected. They read the account now.

### 2.4 Note on the 'System' option

There is **no "System" (follow the operating system) choice** — only Light and Dark. The controller previously claimed to accept it but the column cannot hold it, so the rule was aligned to the column rather than the option being added. Adding it properly needs a migration to widen the column and is a deliberate decision, not something to slip into a bug fix. Raised as an open item in §6.

### 3.1 Commit log

| # | Commit | Title | Files | +/− |

| 1 | `3781f61` | Keep the dark class through an in-app navigation | 1 | +43 / −10 |

### 3.2 Establishing whether this was caused by yesterday's fix

Because the report arrived immediately after a theme change had been delivered, the first question was whether that change caused it. It did not, and this was proven rather than asserted: the theme files were reverted to the commit *before* the fix and the same navigation test was run. **The flip reproduced identically on the older code.**

The defect predates the preference work. It became visible only because the first fix made dark mode persist at all — before that, the theme reset so readily that there was nothing to notice flipping.

### 3.3 What was actually wrong

The preference was never being lost. Through every navigation, `localStorage` still read `dark`. What disappeared was the **`dark` class on the `html` element**, which is what actually carries the theme.

Nothing put it back:

- The class is only ever added at runtime, so it is **not present in the markup the server sends**. An in-app navigation swaps that markup in and the class goes with it.
- Alpine does not restore it either. Its watcher on `darkMode` fires when the value *changes*, and after a navigation the value is read back out of storage unchanged — so nothing notices the class is missing.

| Navigation | Before | After |
|---|---|---|
| Projects | flipped to light | holds dark |
| Inventory | flipped to light | holds dark |
| Products | flipped to light | holds dark |
| Dashboard | flipped to light | holds dark |
| Settings | flipped to light | holds dark |
| Toggle, then navigate immediately | flipped to light | holds dark |

Every navigation flipped. Every one now holds.

### 3.4 What changed

The theme is applied from storage on every navigation as well as on load. The listener is registered **once**: it lives on `document`, which survives the body swap, so re-running the script on each navigation would otherwise stack another copy of the same handler — the same trap the form submit guard hit previously in this project.

### 3.5 A second correction, to yesterday's own change

The 24 August fix wrote the account preference into `localStorage` on **every** page load. That carried a race: the value baked into a page is read when that page is rendered, so toggling the theme and immediately reloading could let a page rendered before the change reached the server undo a choice the user had already made and could see.

The account preference now **seeds** a browser that has no value of its own, rather than overwriting on every load. Once a browser holds a value, that value is the live one. The race is gone.

**Trade-off, stated deliberately:** a new browser or machine still picks up the theme from the account, which was the original goal. But changing the theme on one machine will no longer propagate to another machine that already has a value of its own. Continuous cross-device sync would need the preference re-checked on each load, which reintroduces the race. If the client wants true multi-device sync, it should be built as its own piece of work — see §6.

## 5. Correction — a regression introduced and caught

Recorded in full because it is the kind of failure that matters.

While writing the 24 August fix, the route name was written from memory as `settings.theme`. The actual name is **`settings.update-theme`**. `route()` throws on an unknown name, and the call sat in the main layout — so **every authenticated page returned 500**.

It was caught by the verification sweep, which showed all five checked pages failing rather than rendering. It was fixed and re-verified before the commit was made, and **was never pushed** — no version containing it reached the repository or the client.

Two things follow from it, both applied for the rest of the work: route names are checked against the router rather than recalled, and a change to a shared layout is swept across multiple pages before it is committed, because the blast radius is every page rather than one.
