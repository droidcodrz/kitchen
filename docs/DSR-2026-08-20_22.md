### 2.2 Edit form — confirming a project reserved nothing

Setting a project's status to **Confirmed** on the edit form changed the status and nothing else. No materials were reserved, so inventory read as untouched while the project was live and consuming planning capacity.

Creating a project already confirmed reserved correctly, and so did the Change Status dialog — only the edit form was missing it. That is precisely why the stock logic had tested clean previously: testing had gone through the dialog.

`updateProject` now releases any existing reservation before the products and inventory items are synced, then reserves again against what the project holds afterwards. The order matters — releasing after the syncs would give back quantities for the *new* set of materials rather than the ones actually reserved.

*Verified:* edit-to-confirmed reserves; repeated saves do not accumulate; changing quantity recalculates; confirmed back to draft releases; the dialog still works; consumed stock untouched on an in-production edit; shortage still blocks production.
`ec5feb9` — `app/Services/ProjectService.php`

### 2.3 Waste bin — restoring a confirmed project took nothing back

Deleting a confirmed project correctly handed its reserved materials back to inventory. Restoring it from the waste bin took nothing again. The project was live once more while nothing was held for it, so available quantity read higher than reality — and because the figure is cumulative, the gap survived every later calculation.

`TrashController::restore` now reserves again when the restored item is a project still in Confirmed status. Draft takes nothing; in-production and later are left untouched, as they had already consumed their stock and were never released on delete.

*Verified:* full cycle — confirm reserves, delete releases, restore reserves again; a second delete-and-restore round leaves the figure unchanged rather than accumulating.
`d103a5f` — `app/Http/Controllers/TrashController.php`

### 2.4 In-production projects — material changes were silent

Adding a product to a project already in production did nothing to inventory: the product's materials were neither deducted nor reserved, so the project was building something stock had no record of. Removing a product was equally silent, leaving materials written off that had gone back on the shelf.

Editing such a project now settles the difference — taking what was added, returning what was removed — and refuses the save outright when stock cannot cover an increase. The whole update runs in one transaction, so a refusal leaves the project exactly as it was rather than half-saved and claiming materials that were never deducted.

**Shortage reporting.** Every short item is now collected before anything is deducted and named with its figures, so the message reads `not enough stock: Steel Sheet (available 3, needed 5 sheet)` instead of failing on the first item and hiding the rest. The same detail goes to the configured recipients as an in-app notification and an email, under a new `insufficient_stock` alert type that can be routed and switched off like the others.

**One implementation note worth recording.** The alert is raised from the controller, after the failed work has rolled back — not from the service. Raised any earlier it sits inside the doomed transaction and is rolled back with it, which silently loses the in-app notification while the email, not being transactional, still goes out. The result would be an email with no matching record in the system.

*Verified:* on creating a project, editing one, and moving one into production — the form keeps what the user typed and shows the shortage. Confirmed, draft and delete/restore behaviour unchanged.
`312082a` — `ProjectService`, `InventoryService`, `InsufficientStockException`, `InsufficientStockNotification`, migration, controllers

### 2.5 Reservation ledger recorded gross movements, not net

Editing a confirmed project released the entire old requirement and reserved the entire new one. The running total came out correct, but adding a single unit was recorded as **"released 5, reserved 6"** — which reads as though five units were freed and six taken, and leaves two large movements in the ledger for a change of one.

This was raised during review of the figures and was a fair criticism: a project already in production was settled by difference, while a confirmed one was settled in full. The same situation was being handled two different ways depending on status.

Adding one unit now reserves one unit and the ledger says so. Full reserve and release still happen where they should — on confirmation, and when a project stops being confirmed. A save that changes nothing now writes no transaction at all, where previously it wrote a release and a reservation of the same size.

*Verified:* across confirm, add, remove, quantity change, no-op save, status changes both directions, delete/restore, production consumption and the shortage guard — and through the edit form in a browser, where adding one unit takes reserved from 5 to 6 and logs a single reservation of 1.
`f46b010` — `ProjectService`, `InventoryService`

### 2.6 Repair command for figures that had already drifted

`reserved_quantity` is kept as a running total: added on confirmation, subtracted on release. Any interruption in that sequence leaves the total wrong, and because it is cumulative the error stays there instead of correcting itself on the next save. The four defects above had been leaving exactly that kind of residue.

`inventory:recalculate-reservations` recomputes the figure from the projects that actually hold a reservation rather than adjusting the existing one, so it repairs drift whatever caused it. `--dry-run` prints the corrections without writing; running it twice is a no-op. Only confirmed projects are counted. Stock quantities are never modified, only reservations.

`b04865f` — `app/Console/Commands/RecalculateReservations.php`

### 2.7 Deployment — two undocumented dependencies

Notifications, emails and the recurring stock and deadline checks all depend on two background services that had never been documented: a **queue worker** and the **scheduler cron**. Neither was running. At the time of writing, 55 jobs had accumulated unprocessed — meaning every notification the application has ever queued is still sitting in that table, undelivered. Mail transport was additionally set to `log`, writing mail to a file rather than sending it.

`docs/SERVER-SETUP.md` covers both, with Cloudways steps, a fallback for hosts without a process manager, the mail transport, and a troubleshooting table keyed by symptom. `deploy.sh` runs the deploy steps in order and always calls `queue:restart` — a running worker holds the previously deployed code in memory and never picks up new code by itself, so skipping that step makes a deploy appear to have done nothing.

A follow-up commit added the frontend build. Both `vendor/` and `public/build/` are gitignored, so a fresh checkout has neither: missing `vendor` stops artisan before it starts, and missing `public/build` returns **500 on every page** because the layout asks Vite for a manifest that was never generated. Neither is a code fault, but both present as one.

*Verified:* against a clean clone of the branch — 47 migrations with no failures, seeded, and the project detail and edit pages, products and inventory lists and the Required Materials section all loading correctly.
`369682c`, `1c26a87` — `deploy.sh`, `docs/SERVER-SETUP.md`

### 4.2 Duplicate project lines silently discarded data

**Reported:** *Add Project — duplicate product and inventory item allowed.*

Adding the same entry twice did not add up. The rows are synced keyed by id, so the second row silently overwrote the first and its quantity was lost. A project listing a product at quantity 2 and again at quantity 3 saved a **single row of 3**, with nothing to indicate the 2 had been discarded.

Both forms now refuse the save and name the repeated entry, so the user can combine the rows into one with the correct total. Applies to products and inventory items independently — the same id may still appear once as a product and once as an inventory item, since those are different things. Blank rows are ignored, as both forms render an empty row by default.

A follow-up moved the guard forward in the flow: the dropdown now greys out anything already chosen in another row, on the create page, the edit page and the New Project modal, so the duplicate cannot be selected in the first place. Validation remains as the backstop for anything posted directly.

The modal needed a fix before this could work at all — its product select had no `x-model`, so the chosen id never reached the row it belonged to and there was nothing to compare against. Its inventory select had the same gap.

*Verified in a browser on all three forms:* the chosen option is disabled in the next row, every other option stays selectable, saved lines still load with their quantities, and a normal save succeeds with both intact.
`55eb931`, `8b9f145`

### 4.3 The test suite was pointing at the working database

**Severity: highest of this period.** Found while running the suite, not reported by QA.

`phpunit.xml` had its `DB_CONNECTION` and `DB_DATABASE` lines commented out, so the suite ran against whatever `.env` pointed at. The tests use `RefreshDatabase`, which drops every table before each test. Running the suite therefore wiped the working data — **and on a machine configured against the live database it would have dropped that instead.**

This was not theoretical: it destroyed this environment's data mid-session, which is how it was found. It is now pinned to an in-memory database so a test run cannot reach real data.

Two further problems surfaced once the suite could run:

- `UserFactory` still built a single `name` column, which the users table replaced with `first_name` / `last_name` some time ago. Every test that created a user died on the insert, taking most of the suite with it.
- The remaining assertions described the old starter application rather than this one — the root URL redirects to login rather than serving a landing page, and deleting an account soft-deletes it deliberately so the row survives for the audit trail.

**Suite went from 21 failing / 4 passing to 23 passing.**

`f475a96` — `phpunit.xml`, `UserFactory`, `ProfileTest`, `ExampleTest`

### 4.4 Public self-registration removed from the web and the API

Found while fixing the profile form (§4.5), which shares the same root cause.

Two endpoints allowed anyone who could reach the server to create their own account on an internal manufacturing system:

- `GET|POST /register` — the web registration form.
- `POST /api/register` — the worse of the two. It sits outside CSRF and outside auth, and returned a **working Sanctum API token** on success, so a caller obtained an account and the means to use it in a single request. The account was created with no role attached.

Both were non-functional at the time because they insert the same missing `name` column — but that is an accident of an unrelated bug, not a control. Repairing that column would have opened both doors.

Accounts already have a supported path: **Settings → Users**, where an administrator creates a user and assigns a role at the same time. The routes, controller and view were removed, along with both paths in the OpenAPI documents so the client is not shown endpoints that no longer exist. The welcome page link is wrapped in `Route::has('register')` and stops rendering on its own.

*Verified:* `/register` and `POST /api/register` both return 404; login still works; Settings → Users still creates accounts. A sweep of every remaining route confirmed all of them stay behind auth — unauthenticated requests redirect to login, unauthenticated posts are refused by CSRF.
`b497e5b`

### 4.6 Products and inventory items could not be edited at all

**Reported:** *Edit Product — Inventory Type missing*, then *same issue on Edit Inventory*.

The reported symptom was a missing dropdown value; the actual situation was worse. **Neither an inventory item nor a product could be saved from its edit form.** Material Type was marked required, and no record in either table carries one, so every form opened with a required field that was empty and could never be submitted.

Two distinct causes, both fixed:

- **The lists were empty.** The seeder that fills `dropdown_options` existed but was never registered, so the table was empty on every install. Item Type, Material Type, Material Grade, Thickness Gauge and Inventory Type all read from it, so each rendered with no options at all — and a product's saved value had no matching option to appear as selected, which read as the value having been *lost* rather than merely unlistable. The seeder is now registered for new installs, and a migration runs it against existing databases, which are not re-seeded on deploy. It matches on type and value before inserting, so it adds nothing twice and leaves hand-edited options alone.
- **Material Type is now optional** on both forms. It is genuinely absent from every record, and plenty of items — a sensor, a control panel, a valve — have no meaningful material type. Label generation already handled it being missing.

Additionally, a saved value that is not in the option list is now listed as its own option marked **"(not in list)"**. The record shows what it actually holds, the form can be saved without silently rewriting it, and the value survives.

The Add Product modal also listed three inventory types of its own rather than reading the shared list, leaving two unreachable there; it now uses the same source as the create and edit forms.

*Verified in a browser:* products saved as Raw Materials and Merchandise Goods each show their type on Edit; all four other dropdowns populate; a product created through the modal as Consumables opens in Edit showing Consumables; three further inventory items are submittable where none were before; and a save preserves an `item_type` that has no matching option rather than clearing it.
`2aee5a8`, `109fc81`

### 4.8 Same-name product and inventory item were indistinguishable

**Reported:** *Add Project — same name product and inventory item cause confusion.*

A product and an inventory item can legitimately share a name, and the selection lists gave no way to tell them apart once they did. The modal was worst: its product options carried the name alone with no reference of any kind, while an item with a blank SKU rendered as a name followed by an empty pair of brackets.

Every option now names its type and appends the reference only when one exists — `Steel Panel (Product - PROD-SP-001)` against `Steel Panel (Inventory item - MAT-SP-001)`, and `Stainless Steel Sheet 304 (Inventory item)` where no SKU exists.

This distinguishes rather than prevents: a manufactured product and the raw material it is cut from sharing a name is normal, and refusing it would block real data to solve a labelling problem.

*Verified in a browser* on all three forms with a product and an inventory item deliberately given the same name.

### 4.9 Inventory custom fields — scoping and display

Two related reports, addressed in three commits.

**Reported:** *Settings → Custom Fields → Inventory — categories not reflected in Add Inventory.*

Inventory items have **no category column at all** — they are matched on *system category* through `applies_to_item_types`. That field was on neither form and in neither set of validation rules, so `validated()` dropped it and an inventory custom field could not be scoped to anything. The "Category" selector shown on that screen lists `Category` records, which inventory never uses; whatever was picked there was stored and then never read.

Both forms now show the system categories as checkboxes when *Applies To* is Inventory Items, and the Category selector is limited to Products. Two traps were closed on the way in:

- Both selectors sit on the same form and only one is ever *shown*, so the hidden one still posts whatever was last picked — an inventory field would have carried a category nothing reads.
- Unticking every checkbox posts no key at all, so `validated()` omitted it and the previous scoping stayed in place, leaving no way to widen a field again.

The edit form also re-renders a stored system category that has since been renamed as a ticked "(not in list)" box, so it does not quietly fall off on the next save and widen the field to every item. The definitions list now prints an inventory field's real scope instead of always saying "All categories".

A follow-up added a link to **Settings → Dropdown Options → System Category** beneath the list, and a plain message when nothing is configured, after the list appearing short was reported as a suspected fault in the form itself. The list is only ever as long as the entries configured there.

**Reported:** *Add Inventory — custom fields display without trigger selection.*

The Additional Fields panel is driven by `x-show`, which Alpine can only apply once it has booted. Until then the browser paints the element as it stands in the markup — so the panel was on screen **from first paint**, before any System Category had been chosen, which is exactly the trigger it is meant to be waiting for. It disappeared a moment later once Alpine caught up, and would stay on screen permanently if Alpine ever threw on that page.

`x-cloak` is the standard pairing for this and the rule for it is already in the stylesheet; every other conditional block on these forms uses it. Six had missed it: Inventory add/edit/list and Product add/edit/list.

*Verified by loading the page with JavaScript disabled*, which reproduces the pre-boot state exactly: the panel was visible on Add Inventory and Add Product before the change and hidden on both after it. With Alpine running the behaviour is unchanged — nothing selected shows no fields, picking a category shows the fields scoped to it plus those set to all categories, and clearing the selection hides them again.
`aaed7b5`, `ca2c48b`, `0c7106b`

## 5. Corrections and judgement calls

Recorded for transparency.

**A calculation criticism that was correct.** The reservation ledger was challenged on the grounds that adding one unit should move the reserved figure by one, not release five and reserve six. That was right, and the underlying inconsistency — confirmed projects settled in full, in-production projects settled by difference — was real. Corrected in `f46b010` (§2.5).

**Registration left deliberately broken, then removed.** When the profile fix (§4.5) exposed the same `name` mismatch in `RegisteredUserController`, it was left unfixed rather than repaired in passing, on the grounds that making public registration *work* on an internal system was a decision to take deliberately rather than a side effect of a bug fix. It was raised as an open question and removed once confirmed (§4.4). The one failing test at that point was the deliberate marker.

**Scope deliberately not widened.** The CSP was not loosened to admit the font CDN (§4.10); the unused links were removed instead. Widening a security policy to accommodate dead markup would have been the easier change and the wrong one.
