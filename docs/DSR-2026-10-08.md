## 3. The feature

**Requested:** *"there should be an option to change logo or name on product also to change on login page in settings"*

Read as the application's own branding — the name and logo users see — rather than an image per product. Confirmed with the client at delivery; if per-product images were meant, that is a separate piece of work.

### 3.1 What was built

A **Branding** section on the Settings page, visible to administrators only, holding the application name and a logo upload. Both are applied in three places: the login screen, the sidebar, and the browser tab title.

Before this, the name was written into the Blade templates and the logo was an inline icon, so putting a client's own branding on screen meant editing templates and redeploying.

### 3.2 How the upload works

As instructed — *"images waise hi upload hongi jaise pdf ho rhi thi aur wahan hi save hongi"* — the logo takes exactly the same route as a project attachment: stored on the **private disk** under its own folder, never written into the web root, and served back through a controller.

### 3.3 Decisions worth recording

**The logo's serving route sits outside authentication.** The login screen displays the logo, and a sign-in page cannot fetch an image that requires being signed in. The handler only ever streams the one path held in settings, never a path taken from the request. **This decision is central to §4.**

**SVG is not an accepted format.** It can carry script, and the logo renders on a page every user loads. The rule also checks the file really is an image rather than trusting its extension.

**Clearing the name restores the default** rather than leaving the application nameless.

**A replaced logo is written before the previous one is deleted**, so a failed write cannot leave the installation with no logo at all. The URL carries a version so browsers do not keep serving the old file.

**The logo component reads the setting itself** instead of taking it from the surrounding view. A Blade component has its own scope, so data handed to the layout by a view composer does not reach into it — relying on that would have left an uploaded logo permanently invisible. This was caught before delivery.

## 4. The reported fault, and what it actually was

**Reported:** the logo shows as a broken image on the login page. Reported repeatedly through the day against several attempted fixes.

### 4.1 The actual cause

The `branding/logo` route had ended up **inside the authenticated route group** on the client's machine.

The changes were being applied by hand rather than pulled, and in `routes/web.php` the route was placed among the Trash routes — which sit inside `Route::middleware(['auth', 'verified', 'no-cache'])->group(...)`. The repository has it outside that group, where it was written.

Consequence: a visitor on the login page is not signed in, so the request for the logo was redirected to the login page. The browser received an HTML redirect where it expected an image, and drew a broken icon.

**Verified by moving the route into the auth group locally and requesting it as a guest:**

```
Route inside the auth group   ->  302 redirect to /login     (broken image)
Route outside the auth group  ->  200 image/png              (correct)
```

### 4.2 Why it took so long

Every server-side check passed, because server-side everything *was* correct — the table, the settings, the file on disk, the file size, the content type, the route being registered. The request was being turned away by middleware before it reached any of it, and a redirect is not an error, so nothing was written to any log.

The diagnostic command built during the day (§5) reported the route as "registered", which was true. It did not check **which middleware the route sits behind**, and that was the one thing that mattered.

### 4.3 What would have found it sooner

The symptom was always described as the logo missing **on the login screen**. Under this fault the logo displays correctly everywhere else — the sidebar, the browser tab — because those pages are only reached once signed in.

Asking *"does the logo appear in the sidebar after you log in?"* would have pointed at authentication immediately. That question was never asked. Instead the day went into the serving mechanism, the content type, and URL generation.

## 5. The other eight commits

These were not the reported fault, but four of them fixed real defects that would produce the same symptom on other installations. They are listed with what each was actually for.

### 5.1 `8157f06` — a missing table staying missing for an hour

A page served before the settings table exists falls back to an empty set so it still renders. That fallback was being written into the cache under the same hour-long lifetime as a real result, so once the migration finally ran, every page would have carried on showing the default name until the hour was up — indistinguishable from the feature not working.

The fallback is now returned for that one request and never stored.

The test for it goes through the query builder rather than the model, because saving through the model fires its own cache invalidation and hid the problem entirely. **Confirmed the test fails against the previous version.**

Also in this commit: a `GET` on `settings/branding` answered with an exception page. Nothing in the application requests that address with GET — the form posts to it — but a refresh or a back button after a save does. It redirects to Settings now.

### 5.2 `d55ec74` — a content type that did not depend on detection

The logo was served without a type of its own, leaving the framework to detect it from the file. Detection needs the `fileinfo` extension, which is not always enabled — and the application sends `X-Content-Type-Options: nosniff`, so the moment the type comes back wrong or empty the browser refuses to render the image rather than guessing.

The type is recorded at upload and sent explicitly. It arrives from the browser, so it is checked against the three types a logo may be; a spoofed `text/html` was tested and comes back as `image/png`.

### 5.3 `0298b9e` — an upload recording half of itself

The guard after storing the file checked only for an outright `false`, so a null or empty path went straight past it and the settings were written as though the upload had worked: the path saved as nothing while the type and version said a logo was there.

**This state was found in the client's live database**, which is how it was identified:

```
logo_path      (empty)
logo_version   1791470616
logo_mime      image/png
```

The result is now checked for being empty as well as false, and the file is confirmed on disk and non-empty before any setting is written. The failure message names the likely cause rather than asking the user to try again at nothing.

Removing a logo now clears its type and version too; leaving them behind produced the same misleading state from the other direction.

### 5.4 `798b495` — streaming the file out

The logo went out through `$disk->response()`, which streams with `fpassthru()`. Some hosts disable that function in `php.ini`, and when it is disabled the response arrives empty — no exception, no log line.

**This application had already been caught by this once.** The attachment download carries a comment saying exactly that and uses `response()->download()` for the reason. The same trap was walked into on the logo. It now uses `response()->file()`, which uses `readfile()`.

The test asserts the response is a `BinaryFileResponse` rather than a streamed one, so it cannot quietly go back.

### 5.5 `1a0d831` and `a861f6a` — a regression, introduced and reverted

`1a0d831` changed the logo URL from absolute to relative. **That was a mistake and it made things worse.**

A relative path is produced by stripping the root the request came in on. Where an application is not served from the root of the domain — reached as `/public/login` rather than `/login`, which is common on a local machine — that strips the directory the application sits in along with it:

```
request root   http://localhost:8081/public
relative       /branding/logo                              wrong
absolute       http://localhost:8081/public/branding/logo  right
```

`a861f6a` put it back. The test now builds a request arriving under a subdirectory and asserts the URL keeps it; **it fails against the relative version.**

The reasoning behind the original change — that an absolute URL would be built from `APP_URL` — only holds outside a request, and the logo URL is only ever generated while rendering a page. That should have been checked before changing it.

### 5.6 `7dd98a8` and `92e6911` — the diagnostic command

`branding:doctor` checks the environment, the table, the saved settings, the cache, the logo file, the routes and the cached bootstrap files, and names what is wrong with the command to fix it.

It catches one case that hides itself: when a migration is **recorded as run but its table is not there**, `migrate` reports "Nothing to migrate" and exits successfully. This was reproduced deliberately and confirmed. `--repair` clears that single migration's record and runs that single migration, touching nothing else.

`92e6911` added `--fetch`, which requests the logo over HTTP from a base address given on the command line and reports the status, type and bytes that actually came back — separating "the request never arrived" from "it arrived and came back empty". Checked both ways against a running server.

**Both of these were built because the fault could not be found by inspection.** They did not find it either — see §4.2 — but they are worth keeping.

## 6. Corrections

Recorded plainly.

**A regression was introduced and shipped.** `1a0d831` made the logo URL relative, which breaks any installation not served from the root of a domain. It was live for four commits before being reverted in `a861f6a`. It was changed on reasoning that did not hold, without testing the case it broke.

**A route-name error took every page down locally.** During earlier work the route name was written from memory as `settings.theme` where the actual name is `settings.update-theme`. `route()` throws on an unknown name and the call sat in the main layout, so every authenticated page returned 500. Caught by the verification sweep before the commit and **never pushed**.

**A commit was made with a failing test.** A test-isolation problem left one test failing in the full suite while passing alone. Caught before pushing, fixed, and confirmed stable across three runs.

**A test was written that proved nothing.** The first version of the missing-table test passed against the broken code as well as the fixed code. It was rewritten to go through the query builder and confirmed to fail against the old version before being kept.

**A test was removed rather than left misleading.** Faking a disk that accepts a write and then has nothing to show for it fought the storage fake instead of exercising the code, and passed for the wrong reason. The branch it was meant to cover is therefore **not under test**; what is covered is the invariant it protects.

**Several hours went into the serving mechanism when one question would have found the fault.** See §4.3.
